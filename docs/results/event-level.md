# 이벤트 단위 평가 — 실사용 지표 (2026-09-30)

창 단위 `@300/h macro-F1` 은 **후처리 이전**의 값이라 실사용 성능이 아니다.
설계한 후처리(연속 프레임 다수결 + 이벤트 병합 + 쿨다운, `docs/uart-protocol.md`
3절)를 거친 뒤의 **이벤트 recall** 과 **회/일 오경보**를 낸다. 재학습 없음,
기존 체크포인트의 출력만 후처리했다.

---

## 0. ★ 테스트셋 창을 쓰지 않았다 — 쓰면 낙관적으로 틀린다

테스트셋의 창은 클립당 점수 순으로 골라 뽑은 것이라 **시간적으로 떨어져
있다**: 같은 클립 창 간격 중앙값 **2.0초**, 실제 hop 0.25초와 붙어 있는 쌍은
**0%**. 그 위에서 k/m 다수결을 돌리면 떨어진 창들의 오류가 서로 독립에 가까워
**다수결이 실제보다 잘 듣는다** (`eval_confusion.py` 의 기존 경고,
`stream_eval.py` docstring).

→ **원본 오디오를 hop 250ms 로 빈틈없이 다시 훑었다** (`tools/event_eval.py`).
실기기가 상시 구동에서 보는 것과 같은 프레임 열이고, 인접 프레임이 0.75초를
겹쳐 오류가 함께 간다.

| split | 원본 | 배경음 시간 | 전체 오디오 | 프레임 |
|---|---:|---:|---:|---:|
| test | 2,320 | **4.69h** | 6.45h | 84,104 |
| train 1/4 (검증용) | 1,539 | 2.47h | 3.4h | — |

## 1. ⚠️ 먼저 — **1회/일 지점은 이 테스트셋으로 분해할 수 없다**

배경음 총 재생시간이 **4.69시간**뿐이다.

> 오경보를 **0회 관측**해도 95% 상한은 `3 / 4.69h = 0.640회/h = **15.4회/일**`.

즉 "1회/일" 을 주장하려면 관측만으로는 **최소 72시간**의 배경음이 필요하다
(3/72h = 1.0회/일). 아래 표의 "목표 1회/일" 행은 **문턱값을 0회 관측이
될 때까지 올린 것**이고, 실제 1회/일을 확인한 것이 **아니다.**

→ 이 지점의 확정은 **보드 8시간 무인 구동(G7)** 과 v2 배경음 확충으로 미룬다.
아래에서는 **1회/h** 를 주 동작점으로 쓴다.

⚠️ 해상도도 낮다. 4.69시간에서 이벤트 1개 = **0.213회/h** 다. 목표 1/h 에
가장 가까운 실현값이 0.854/h(4개)인 이유다.

## 2. 원본 길이 분포 — `glass` 가 m/k 규칙에 불리하다

hop 250ms, 창 1.024초 → 길이 L 초 클립의 프레임 수 = `(L−1.024)/0.25 + 1`.
**1.5초면 프레임 2개**뿐이라 3/4·3/5 규칙을 원리적으로 만족할 수 없다.

| 클래스 | 클립 | 총 시간 | 중앙 | ≤1.5s (프레임 ≤2) | ≤2.5s |
|---|---:|---:|---:|---:|---:|
| siren | 75 | 14.4분 | 8.2s | 1% | 7% |
| **glass** | 154 | 12.3분 | 2.7s | **28%** | **44%** |
| scream | 191 | 19.4분 | 3.4s | 21% | 36% |
| dog_bark | 447 | 59.1분 | 4.0s | 15% | 23% |
| background | 1,605 | 281.9분 | 8.2s | 8% | 15% |

→ **`glass` 의 낮은 이벤트 recall 에는 규칙상의 불리함이 섞여 있다.**
유리 파손이 0.3초 과도음이라는 클래스 성질과 3/4 규칙이 충돌한다.
실기기에서는 이벤트 앞뒤로 실제 환경음이 이어지므로 이 불리함은 **데이터셋의
클립 경계가 만든 것**이고, 실배치에서는 덜할 수 있다.

## 3. 격자 선택 — **검증(train 1/4)에서 3/4, 테스트는 한 번만**

목표 1회/h 에서 macro 이벤트 recall 기준.

| (m/k) | ① mel | D-1(√) |
|---|---:|---:|
| 1/1 | 0.5281 | 0.0621 |
| 2/3 | 0.5166 | 0.0640 |
| **3/4** | **0.5342** | **0.1116** |
| 3/5 | 0.5305 | 0.0757 |

**두 모델 모두 3/4 가 최선**이라 같은 설정을 쓴다.

### 쿨다운은 recall 에 **원리적으로** 영향이 없다

`c ∈ {0, 2, 5}s` 가 recall 을 소수점 4자리까지 바꾸지 않았다. 버그가 아니다 —
**쿨다운은 반복 발화만 지우고 첫 발화는 항상 살아남는데, recall 이 "원본당
한 번 이상" 이기 때문**이다. 실제로 이벤트 총수는 줄어든다 (검증셋 3/4 에서
397 → 323 → 291개). 다만 **1회/h 동작점에서는 남은 오경보가 이미 서로 다른
클립에 하나씩** 있어 쿨다운이 구속하지 않는다.

→ 쿨다운의 값어치는 **오경보 총수와 반복 알림 억제**이지 검출률이 아니다.
보고는 `c = 2s` (펌웨어 `GAP_MS` 와 맞춤)로 한다.

⚠️ **한계**: 검증 부분집합이 **학습에 쓰인 원본**이다. 그래서 그 표의 절대
수치(0.53)는 낙관적이고, 테스트(0.165)와 크게 벌어진다. 우리는 거기서
**(m/k, c) 선택만** 했고 최종 수치는 테스트에서 한 번만 쟀지만, **선택 자체가
과적합된 조건에서 이뤄졌다**는 한계는 남는다. 순위가 두 모델에서 일치한 것이
그나마의 방증이다.

## 4. ★ 테스트 결과 (3/4, cd 2s, 한 번만 측정)

### 동작 곡선

| 목표 오경보 | 실제 | ① mel macro recall | D-1(√) macro recall |
|---|---:|---:|---:|
| 30회/h | 29.9/h (717/일) | 0.4543 | 0.3401 |
| 10회/h | 9.8/h (236/일) | 0.3491 | 0.1987 |
| 3회/h | 3.0/h (71.7/일) | 0.2529 | 0.1126 |
| **1회/h** | **0.854/h (20.5/일)** | **0.1652** | **0.0924** |
| 1회/일 (미분해) | 0회 관측 | 0.0669 | 0.0370 |

### 주 동작점 1회/h — 클래스별

| 구성 | `siren` | `glass` | `scream` | `dog_bark` | **macro** | 오분류 발화 |
|---|---:|---:|---:|---:|---:|---:|
| **① log-mel** | 20% | **2%** | 7% | 37% | **0.1652** | 1 |
| **D-1(√)** | 3% | 4% | 7% | 23% | **0.0924** | 6 |

원본 수: siren 75 / glass 154 / scream 191 / dog_bark 447.

### 읽기

1. **실사용 지표는 창 단위보다 훨씬 낮다.** ① 의 창 단위 `@300/h macro-F1
   0.673` 과 이벤트 `@1/h macro recall 0.165` 는 **같은 것을 재지 않는다** —
   전자는 창당 300회/h 오경보를 허용한 지점이고, 후자는 **이벤트 1회/h** 다.
   후처리가 창 오경보를 이벤트로 접으면서 동작점이 훨씬 엄격해진다.
   → **발표·논문에서 "0.673" 을 실사용 성능처럼 말하면 안 된다.**
2. **① 이 D-1(√)보다 모든 동작점에서 앞선다** (1/h 에서 1.8배). 창 단위에서
   본 격차가 이벤트 단위에서도 유지되고, 오히려 벌어진다.
3. **오분류 발화**(이벤트를 다른 이벤트로)는 ① 1회 vs D-1(√) 6회. 파형 구성이
   클래스를 더 자주 혼동한다.
4. **`glass` 가 ① 에서 2%로 무너진다.** 2절의 규칙상 불리함(28%가 프레임 2개
   이하)과 겹친다. 창 단위에서는 glass 가 ① 의 강점 클래스였다(47.1%)는 점과
   대비된다 → **후처리가 짧은 과도음을 죽인다.**
   → 실기기에서는 `glass` 에만 다른 (m/k) 를 쓰는 것이 합리적이다. 클래스별
   규칙은 `eventmerge.py` 에 넣을 수 있다 (지금은 전 클래스 공통).

## 5. 하지 않은 것

- **PANNs zero-shot 의 이벤트 단위 평가.** 빈틈없는 스캔이 84,104프레임 ×
  99ms = **약 2.3시간** 이라 이번에 돌리지 않았다. `ceiling_check.py` 의 창
  단위 결과는 있다 (`docs/results/ceiling-check.md`). 필요하면 별도로 돌린다.
- **3시드 평균.** ① 과 D-1(√)의 다른 시드는 빈틈없는 스캔을 다시 해야 한다
  (모델당 약 6분). 지금은 **각 s1 단일 실행**이다.
- **1회/일 동작점의 실측.** 1절 — 테스트셋으로 분해 불가.

## 6. 산출물

```
tools/event_eval.py                       빈틈없는 스캔 + 후처리 격자
data/eventcache/{tag}-{split}-hop250.npz  로짓 캐시 (모델당 한 번)
data/logs-local/event-grid-{mel,d1sq}.json    검증 격자
data/logs-local/event-test-{mel,d1sq}-s1.json 테스트 (선택 설정)
data/logs-local/event-curve-{mel,d1sq}-s1.json 동작 곡선
```

재현:
```bash
# 1) 스캔 (ai8x venv, 모델당 약 6분)
~/ai8x-training/venv/bin/python tools/event_eval.py --scan \
    --tag mel-s1 --split test --config mel --checkpoint <ckpt>
# 2) 검증 격자 → 설정 선택
python3 tools/event_eval.py --tag mel-s1 --split trainevery4 --grid --targets 1
# 3) 테스트 한 번
python3 tools/event_eval.py --tag mel-s1 --split test --mk 3/4 --cooldown 2 \
    --targets 1,0.0417
```

## 7. 이 결과가 바꾸는 것

- **G1/G2/G7 의 목표 수치를 이벤트 단위로 다시 써야 한다.** CLAUDE.md 8장의
  목표는 창 단위 전제였다.
- **후처리 규칙이 클래스별이어야 한다** — `glass` 는 3/4 로 죽는다.
  `docs/uart-protocol.md` 3.2 의 `START_FRAMES` 를 클래스별로 두는 안을
  열어 둔다 (지금은 전 클래스 1).
- **테스트셋 배경음이 모자란다.** 4.69시간으로는 1회/일을 못 잰다.
  v2 에서 배경음 원본을 늘리는 이유가 하나 더 생겼다 (기존 이유: 하드
  네거티브 비중 49.9%).
