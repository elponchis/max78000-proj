# 증분 전처리 실험 — 설계 (2026-10-20, 보드 미접촉)

**결론부터.** 지시받은 두 증분안은 **이미 주 표에 들어 있다.** 가·다·간격 400·①′ 의 CPU
전처리 지연은 판단마다 새 프레임(4 / 5 / 10 / 16개)만 계산하는 증분 값이고(`synthesis-check.md`
§14.1·§12.1, "증분 4회 == 일괄" 비트 일치 0), ②′ 의 p1 은 새 256 ms 청크만 가속기에 넣고 새
4프레임만 읽어 로그를 계산하며 이전 12프레임은 CPU 버퍼에 보관한다(`fe_measure_main.c`, KAT
"CPU 특징 = 호스트 창 전체 정수 경로" 512/512 일치). **새로 잴 점이 없다.** 따라서 "증분 전처리
실험" 은 하지 않기를 권한다. 대신 같은 비용(보드 1회)으로 논문 4절의 핵심 주장("주된 비용은 데이터
이동")을 추정에서 실측으로 바꾸는 **CPU 구간 분해 측정**을 5절에 제안하고 `fe-curve-design.md`
9절에 사전 등록했다.

## 1. ②′ 의 CPU 구간 0.840 ms 분해 — 기존 로그·코드 추정 (측정 아님)

CPU 구간(`fe_cpu_hop`)이 하는 일: ① 가속기 데이터 메모리에서 p1 출력 int32 **2,048 워드**
(32 밴드 × cos/sin 2채널 × 4프레임 × 8위치)를 읽어 |·| 와 8위치 합, ② 밴드·프레임당 정수 로그
`log2_q8` + `log2_q8_to_int8` **128회**, ③ 32×12 버퍼 밀기(384 B memmove), ④ p2 입력 512 워드 포장.

**근거 1 — 변형 3종의 선형성.** 읽는 워드 수 W 와 CPU 구간(코어 사이클, 1000회 최악):

| 구성 | W (워드) | 로그 횟수 | CPU 구간 (사이클) | ms |
|---|---:|---:|---:|---:|
| ②′ | 2,048 | 128 | 84,000 | 0.840 |
| b64 | 4,096 | 256 | 167,800 | 1.678 |
| f31 | 4,096 | 256 | 166,100 | 1.661 |
| b64f31 | 8,192 | 512 | 331,900 | 3.319 |

(②′, b64f31) 두 점으로 직선을 그으면 기울기 **40.35 사이클/워드**, 절편 **≈ 1,400 사이클**
(= ③ memmove + ④ 포장 512 워드, 손계산 1~2k 와 맞는다). b64·f31 은 그 직선 위(오차 < 1 %)다.
워드와 로그가 16:1 로 고정이라 이 자료만으로는 둘을 가를 수 없다 — 아래 근거 2 로 로그를 묶는다.

**근거 2 — 로그 1회의 비용.** `log2_q8` 은 CLZ 1 + 시프트 1 + LUT 1 + 덧셈 1, `log2_q8_to_int8`
은 곱·시프트·클램프 — 호출 포함 **약 25~35 사이클**. 상한은 ①′ V1 의 LUT 로그 실측
(`synthesis-check.md` §12.1b: 로그+양자화 80,474 사이클 / 1,024 원소 = **79 사이클/원소**, float 경로라
더 무겁다). → 128회 = **3.2k ~ 10.1k 사이클 = 0.03 ~ 0.10 ms**.

**근거 3 — 읽기 1워드의 비용.** APB 쓰기는 실측 27.5 사이클/워드(load1: 1,024 워드 0.282 ms;
load2 도 26). 읽기도 같은 APB 경로이므로 비슷하거나 조금 크다. 나머지(84.0k − 1.4k − 로그)를
2,048 로 나누면 **35~39 사이클/워드** = APB 읽기 ≈ 27~30 + |·|·합·루프 ≈ 8.

| 몫 | 사이클 | ms | 비중 |
|---|---:|---:|---:|
| ① 가속기 메모리 읽기 + \|·\| + 8위치 합 | 72.5k ~ 79.4k | 0.73 ~ 0.79 | **86 ~ 95 %** |
| ② 정수 로그 128회 | 3.2k ~ 10.1k | 0.03 ~ 0.10 | 4 ~ 12 % |
| ③④ 버퍼 밀기 + 포장 | ≈ 1.4k | 0.014 | ≈ 2 % |

읽기가 지배한다는 결론은 로그 상한(79 사이클)을 써도 바뀌지 않는다. **이 분해는 추정이다** — 실측
전환은 5절(tick 두 개 추가, 보드 1회).

## 2. NPU 증분안 — 이미 구현돼 있고 비트 일치가 **구조적으로** 성립한다

**현재 ②′ 가 바로 그 설계다.** 판단 1회 = 새 4,096 샘플(256 ms) 청크만 접어(64×64) p1 에 적재 →
p1 추론 → 새 4프레임만 읽어 로그 → 32×16 버퍼를 4프레임 밀고 채움 → p2. 이전 12프레임은 CPU 의
int8 버퍼(384 B)에 남는다.

**"필터 길이만큼의 앞 구간" 은 ②′ 에는 필요 없다.** 이유는 프레임 격자와 필터가 청크 경계를
넘지 않기 때문이다.

- 접기: 위치 p 의 64 샘플 = 스트림 [64p, 64p+64). p1 = Conv1d(k=8, stride 1, **padding=0**) 이므로
  출력 위치 p 는 샘플 [64p, 64p+512) (512탭 Gabor) 만 본다.
- 프레임 f 는 출력 위치 16f .. 16f+7 의 8개를 합한다(`_idx`, `FE_POS_PER_FRAME 16`, `FE_POOL_POS 8`)
  → 샘플 **[1024f, 1024f+960)**. 프레임 간격 1,024 샘플(64 ms)에 960 샘플만 쓰고 64 샘플은 버린다.
- 청크 c = 샘플 [4096c, 4096c+4096) = 프레임 4c..4c+3. 마지막 프레임의 끝 1024·3+960 = 4,032 < 4,096.
  청크 입력 64 위치에 padding=0 → 유효 출력 57 위치, 프레임이 쓰는 최대 위치 55 < 57.
- 따라서 청크 단위 conv 는 창 전체(256 위치 → 249 위치) conv 와 **같은 정수 연산을 같은 입력에**
  한다. NPU 의 wide int32 누산은 반올림이 없고(int8×int8 합), |·|·합·로그는 CPU 정수 연산이라
  재계산과 증분의 결과가 비트 단위로 같다.
- 정렬 조건: 청크 시작이 64(접기) 와 1,024(프레임) 의 배수여야 한다 — 4,096 이 둘의 배수라 자동.
- 패딩 조건: p1 에 패딩이 **없어야** 한다(있으면 청크 가장자리의 0 패딩과 창 가장자리의 0 패딩이
  다른 위치에 생겨 경계 프레임이 달라진다). ②′·변형 전부 padding=0.

**보드 검증도 이미 끝났다.** 호스트는 창 전체(16,384 샘플)를 한 번에 정수 경로로 계산해 기대
특징 512개를 만들고, 펌웨어는 청크 4개를 차례로 돌려 버퍼를 채운다 → **512/512 일치** (②′ 10-17,
b64·f31·b64f31 10-20, 각 1000회 0 불일치). 프레임이 청크 경계를 넘는 f31 계열(프레임 간격 512 =
8위치, 프레임 [512j, 512j+960))은 지시한 대로 **직전 7위치(448 샘플)를 앞에 붙여** 71 위치를 넣었고
(`FE_FRAME0_OFFSET −1`), 역시 비트 일치했다 — "앞 구간을 붙이는" 증분도 검증된 셈이다.

**남는 비용과 줄일 수 없는 이유.** p1 쪽(load1 0.282 + cfg1 0.023 + infer1 0.080)은 이미 청크만의
비용이다. CPU 0.840 의 ≈ 90 % 인 2,048 워드 읽기는 "새 4프레임의 |cos|·|sin| 8위치" 그 자체라
증분으로는 더 줄지 않는다. 읽기를 8배 줄이려면 8위치 합(그리고 |·|)을 NPU 에 넣어야 하는데,
ai8x 는 wide(int32) 출력 층을 다음 층 입력으로 쓸 수 없어 합 전에 int8 로 떨어뜨려야 한다 →
에너지 정밀도 손실(로그 전 21bit → 8bit), **비트 일치 불가, 재학습 필요** — 10-28 안에는 범위 밖.

## 3. CPU 증분안 — 가·다·간격 400 은 이미 증분이고 reflect 패딩이 원래 없다

- `datasets/melfeat.py` `INC_SPECS`: u1000 (hop 1000, 16프레임, 32멜), u800 (800, 20, 32), h400
  (400, 40, 64). 전부 **패딩 없음·끝 정렬**(`inc_offset`), 학습 특징이 이 정의다. 즉 모델 세 개는
  처음부터 패딩 없는 격자로 학습됐다.
- 펌웨어(`melfeat.c` `melfeat_inc_push`, 링 버퍼)가 ①′ 코드 그대로이고, §14.1 실측이 **push(새
  프레임) + 링 버퍼 풀기** 다: 가 4프레임 223,045 + 3,364 = 2.264 ms, 다 5프레임 2.833 ms, 간격 400
  10프레임 6.188 ms. "증분 4회 == 일괄" 비트 일치 0 (세 구성 모두), KAT 대 `melfeat.py` 1 LSB.
- hop > n_fft 인 u1000·u800 은 프레임 사이 샘플을 건너뛰므로 이력 없이 새 블록에서 바로 뜬다
  (`inc_source`, `MEL_INC_TAIL < 0`); h400 은 꼬리 112 샘플을 보관한다. 둘 다 구현·검증됨.
- reflect 패딩은 **① 원 정의(hop 256 + 창 단위 reflect 128, 64프레임, 판단마다 전부 재계산)** 에만
  있고, 그 구성은 논문 표에 없다. 논문의 16 ms 점은 ①′(hop 250, 패딩 없음)이며 **별도 학습한
  체크포인트**다(패딩을 없애면 특징이 달라지므로 그때 재학습했다 — `melfeat.py` 103~115행).
- → **달라지는 특징도, 재학습도 없다.** 적용할 것이 남아 있지 않다.

## 4. 예상 지연·에너지 — "증분 적용" 값은 현재 주 표와 같다

증분이 이미 들어 있으므로 예상 = 현재 실측. 비교를 위해 **증분을 쓰지 않았을 때**(일괄, 판단마다
창 전체 재계산)의 값을 같은 상수로 추정해 나란히 둔다 — 증분이 이미 벌어 둔 이득의 크기다.
전력 상수: (가) 데이터시트 P_cpu 8.89 / P_load 11.26 / P_npu 40.79 mW, (나) 선행연구 24.8 / 24.8 /
71.7, (나′) Moosmann 24.8 / 24.8 / 35.6. 일괄 전처리 사이클 = 새 프레임 비용 × 전체 프레임 수
(가 16·다 20·400 40·①′ 64; ①′ 는 V1 16프레임 961,282 로 외삽, V0 일괄 실측 45.26 ms 와 같은 급),
②′ 일괄 = 청크 4개 × (load1+cfg1+infer1+cpu).

| 구성 | 전처리 ms (증분 = **현재**) | 판단 1회 ms | E µJ 가 / 나 / 나′ (**현재**) | 전처리 ms (일괄) | 판단 1회 ms (일괄) | E µJ 가 / 나 / 나′ (일괄) |
|---|---:|---:|---|---:|---:|---|
| ②′ | 0.840 | **1.982** | **40.4 / 77.9 / 55.8** | 3.36 | 5.66 | 88.9 / 180.3 / 149.5 |
| 가 u1000 | 2.264 | **2.934** | **43.3 / 97.7 / 78.5** | 8.96 | 9.63 | 102.8 / 263.6 / 244.4 |
| 다 u800 | 2.833 | **3.659** | **53.8 / 121.4 / 97.8** | 11.21 | 12.04 | 128.2 / 329.1 / 305.5 |
| 간격 400 | 6.188 | **9.416** | **166.7 / 353.2 / 261.1** | 24.27 | 27.50 | 327.5 / 801.6 / 709.5 |
| ①′ | 9.868 | **15.057** | **266.8 / 565.0 / 417.5** | 38.7 | 43.9 | 523.1 / 1280 / 1133 |

증분이 없었다면 세 출처 모두에서 가 는 ④(71 / 130 / 78)보다 에너지가 컸고 ②′ 도 ④ 를 넘었을
것이다 — 즉 **논문의 파레토 앞면 자체가 증분 계산 위에 서 있다.** 이 사실은 논문 3절에 "모든
구성의 전처리는 판단마다 새 프레임만 계산하는 증분 방식이며 일괄 계산과 비트 일치한다(보드
확인)" 한 문장으로 적을 가치가 있다(현재는 가·다·간격 400·16 ms 에 "증분 로그 멜" 이라는 말만 있고
②′ 와 비트 일치 언급이 없다). 수치 변경은 없다.

## 5. 대안 제안 — ②′ CPU 구간 분해 실측 (보드 1회)

논문 4절은 지금 "주된 비용은 NPU 연산이 아니라 CPU 가 가속기 메모리에서 결과를 읽어 오는
시간" 이라고 쓰는데, 근거는 CPU 구간 전체(읽기 + 로그 + 포장)의 비중이다. 1절의 추정(읽기
86~95 %)을 **실측**으로 바꾸면 그 문장과 4절 끝 "데이터 이동" 문장이 측정값 위에 선다.

- 변경: `fe_measure_main.c` 의 `fe_cpu_hop` 안에 `tick()` 두 개 — (a) 2,048 워드 읽기 + |·| + 8위치
  합(밴드·프레임별 `e` 까지), (b) 로그 128회 + 버퍼 밀기 + 포장. 계산 순서·결과는 그대로(비트 일치
  유지), 전체 CPU 구간은 (a)+(b)+tick 비용 ≈ 10 사이클. 변형 3종은 같은 코드라 함께 잴 수 있으나
  **②′ 하나면 충분**하다(선형성이 이미 있다).
- 조건: 변형과 같은 결함 수정 펌웨어, POR 뒤 1000회, 1000회 불일치 0 확인. ②′ 주 값(1.982 ms)은
  바꾸지 않는다(8.6절 결정) — 분해 비율만 쓴다.
- 판정·문장: `fe-curve-design.md` 9절.
- 비용: 펌웨어 20분, 빌드·플래싱·POR·1000회 10분, 문서·논문 문장 반영 1시간. **재연결 1~2회
  (플래싱 뒤 POR 1회; UART 가 깨지면 1회 더). 재학습 없음.**
