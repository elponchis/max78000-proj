# 라운드 6 설계 — 로그를 어떻게 되찾을 것인가 (설계만, 2026-09-29)

**전제**: `g8-round5.md` 4.5절의 가설 — "대역 분해는 NPU 로 옮겼고(D-1),
남은 격차는 거의 로그 압축이다" — 가 `①-log72` 로 확정된 경우.

⚠️ **log72 결과를 보기 전에는 착수하지 않는다.** log72 가 `①-cbrt` 쪽에
머물면 원인이 로그 법칙이 아니라 다른 것이고, 아래 설계는 전제가 무너진다.

두 안은 **서로 배타적이지 않다.** (a) 는 로그를 NPU 안으로 넣으려는 시도이고
(b) 는 로그가 하는 일 중 **음량 불변성만** CPU 에서 싸게 사 오는 우회로다.
논문에는 둘 다 "가속기 제약 아래 압축을 되찾는 두 경로" 로 대조해 실을 수 있다.

# (a) NPU 안에서 로그 근사 — 구간선형 오목 함수

## a.1 구성

로그는 오목(concave)이다. 오목 구간선형 함수는 **기울기가 단조 감소하는
ReLU 의 음의 가중합**으로 정확히 쓸 수 있다.

```
f(v) = a·v − Σ_k c_k · ReLU(v − t_k)        c_k > 0,  t_1 < t_2 < ... < t_K
```

`t_k` 를 지나면 기울기가 `c_k` 만큼 줄어든다. `t_k` 를 로그 곡선의 마디에
두고 `c_k` 를 맞추면 로그를 근사한다.

MAX78000 지원 연산만으로 만들면 이렇게 된다 (D-1 의 1층 뒤에 삽입):

| # | 층 | 연산 | 채널 | 하는 일 |
|---|---|---|---|---|
| L0 | `voice_conv1` | Conv1d k=1 + **Abs** | 128 → 100 | 대역 크기 (현행 D-1) |
| **La** | **knot** | **Conv1d k=1 + ReLU**, per-channel bias | **100 → 100K** | `ReLU(v_c − t_k)` |
| **Lb** | **sum** | **Conv1d k=1, 활성화 없음** | **100K → 100** | `a·v − Σ c_k·(...)` |
| L1.. | `voice_conv2` 이하 | 현행 그대로 | 100 → 96 … | |

- `La` 의 가중치는 **블록 대각**이다: 출력 `(c,k)` 는 입력 `c` 만 본다.
  나머지는 0 으로 학습 시작하고, 학습으로 풀어 줄지(자유롭게) 고정할지는
  선택이다. 고정하려면 마스킹이 필요하고 ai8x 에 그 기능이 없다 →
  **자유롭게 두고 초기화만 블록 대각**으로 한다.
- `Lb` 는 `a·v` 항을 위해 `La` 의 첫 K 채널 중 하나를 `t=0` (항등)으로 둔다.
- `t_k` 는 **출력 채널 바이어스**다 → `--use-bias` 가 필요하다.

⚠️ **왜 depthwise 를 못 쓰는가**: MAX78000 은 depthwise separable conv 를
지원하지 않는다 (CLAUDE.md 3장, MAX78002 에서 추가). 채널별 독립 연산을
full 1×1 conv 로 흉내 내야 하므로 가중치의 99% 이상이 0 인 낭비가 생긴다.
**이 낭비 자체가 "가속기 제약이 파이프라인 설계를 강제한다" 는 논문 주장의
사례**라서, 비용을 숨기지 말고 그대로 싣는다.

## a.2 비용 — 442KB / 512KB 안에 들어가는가

`K` = 마디 수. 현재 모델은 가중치 165,376 B (37.4%).

| K | La 가중치 | Lb 가중치 | 추가 | 총계 | 442,368B 대비 |
|---:|---:|---:|---:|---:|---:|
| 2 | 100×200 = 20,000 | 200×100 = 20,000 | 40,000 | 205,376 | **46.4%** |
| 3 | 30,000 | 30,000 | 60,000 | 225,376 | **51.0%** |
| **4** | **40,000** | **40,000** | **80,000** | **245,376** | **55.5%** |
| 6 | 60,000 | 60,000 | 120,000 | 285,376 | 64.5% |
| 8 | 80,000 | 80,000 | 160,000 | 325,376 | 73.6% |

전부 들어간다. **K=4 (55.5%) 를 기본으로 제안**한다 — 로그를 4구간 선형으로
근사하면 42dB 구간에서 오차가 작고, 1.5× 채널 스윕(80.6%)과도 공존한다.

**바이어스 메모리**: `La` 출력이 100K 개이고 각각 바이어스가 필요하다.
MAX78000 의 바이어스 메모리는 **2,048 B 전부**다 (합성 로그 확인).

| K | La 바이어스 | 2,048B 대비 |
|---:|---:|---:|
| 4 | 400 | 19.5% |
| 8 | 800 | 39.1% |
| **20** | **2,000** | **97.7% ← 상한** |

K=4 는 여유롭다. ⚠️ 단 `voice_conv1` 등 다른 층도 bias 를 켜면 함께 먹는다
(9층 전체 bias ≈ 637 B). K=4 + 전 층 bias = 1,037 B → 50.6%. 괜찮다.

**데이터 메모리**: HWC 는 **채널당 8,192 px** 가 한계다 (채널 수 무관).

| 텐서 | 채널 × 길이 | 채널당 px | 총 바이트 |
|---|---|---:|---:|
| L0 출력 | 100 × 128 | 128 | 12,800 |
| **La 출력 (K=4)** | **400 × 128** | **128** | **51,200** |
| Lb 출력 | 100 × 128 | 128 | 12,800 |

채널당 128 px 는 한계의 1.6% 다. 핑퐁 버퍼 기준 동시 최대는
`La(51,200) + Lb(12,800) = 64,000 B` 로 512KB 의 **12.5%**. 여유롭다.

**연산량 — 여기가 진짜 비용이다.**

| | MAC |
|---|---:|
| 현행 전체 | 8,341,248 |
| La (K=4) | 100×400×128 = 5,120,000 |
| Lb (K=4) | 400×100×128 = 5,120,000 |
| **합** | **18,581,248 (2.23배)** |

**추론 사이클이 대략 2.2배 된다** (현행 71,718 → 약 160,000 추정, 100MHz 에서
0.72ms → 약 1.6ms). hop 250ms 의 0.6% 이므로 **실시간 제약에는 여유가 있다**.
그러나 **에너지가 2.2배**가 되므로 G3·G9·G10 의 수치가 전부 바뀐다.
→ 정확도 이득이 이 비용을 넘는지가 채택 기준이다.

⚠️ 위 사이클 수는 MAC 비례 **추정**이다. 확정은 `ai8xize.py` 합성 결과
(`Total ... cycles`) 로 한다 (CLAUDE.md 10장).

## a.3 합성 가능 여부 — 확인해야 할 것 셋

1. **1×1 Conv1d 두 개를 연속으로 놓을 수 있는가.** kws20-v3 yaml 이 이미
   1층에서 `kernel_size: 1` 을 쓰므로 연산 자체는 지원된다. 채널 100→400→100
   의 다중 패스(64 프로세서 초과)가 걸리는지만 보면 된다.
   → `synthesis/safesound-fb-hwc.yaml` 에 두 층을 끼워 `ai8xize.py` 로 확인.
2. **`activate: None` 중간층**. `Lb` 는 활성화가 없어야 오목 합이 보존된다.
   yaml 의 `activate: None` 은 마지막 MLP 에서 쓰고 있으나 **중간 Conv 층에서
   되는지 확인**해야 한다. 안 되면 ReLU 를 두고 **출력에 상수 오프셋**을 주어
   항상 양수가 되게 설계한다 (대역 크기는 비음수라 어렵지 않다).
3. **출력 시프트와 포화.** `Lb` 가 음의 가중합이라 중간값이 int8 범위를
   벗어나기 쉽다. ai8x 의 `output_shift` 로 맞춰야 하고, **QAT 중 포화가
   과하면 근사가 깨진다**. `tools/` 에 활성화 분포 점검을 추가할 것.

## a.4 ★ 가장 큰 위험 — 로그를 **너무 늦게** 건다

L0 의 출력은 이미 **int8** 이다. 즉 대역 크기가 선형으로 int8 양자화된 **뒤에**
로그를 건다. 1 LSB 아래로 내려간 대역은 이미 0 이고, 로그를 걸어도 돌아오지
않는다. 반면 ① 은 **float 로 로그를 건 뒤** int8 로 양자화한다.

→ (a) 가 회복할 수 있는 것은 "1 LSB 위에 남아 있는 값들의 **모양**" 뿐이다.

이 위험이 얼마나 큰지는 라운드 5 가 이미 부분적으로 답한다: `①-cbrt` 가
동적 범위를 24dB 더 담고도 회복하지 못했다 → 손실이 주로 **양자화 바닥**
때문은 아니라는 신호다. 그렇다면 (a) 에도 승산이 있다.

**그래도 사전 확인을 붙인다 (학습 전, 비용 0):**
`①` 의 로그 멜을 취해 **"선형 양자화 → 로그 복원"** 을 시뮬레이션하고
(즉 대역 크기를 int8 로 깎은 뒤 로그를 거는 것), 그 입력으로 ① 모델을
**평가만** 한다. 이 상한이 ① 에 가까우면 (a) 에 승산이 있고, ①-lin 에
가까우면 (a) 는 원리적으로 안 되는 것이다. → `tools/sim_late_log.py`.
**이 확인 없이 학습을 돌리지 않는다.**

## a.5 대안 — 마디를 층이 아니라 **채널 쌍**으로

`La` 의 낭비(99% 0)를 줄이는 방법. L0 를 **100 → 400 채널**로 바로 늘리고
(같은 필터를 K번 복제, 서로 다른 출력 시프트), Abs 뒤에 바로 `Lb` 만 둔다.
- 장점: La 의 5.12 M MAC 이 사라진다 (L0 가 128×400×128 = 6.55 M 로 늘지만
  전체는 더 작다)
- 문제: 마디 `t_k` 는 **Abs 이후의 바이어스**여야 하는데 L0 의 바이어스는
  Abs **이전**에 적용된다. `|x − t|` 는 `ReLU(|x| − t)` 가 아니다.
  → **성립하지 않는다.** 기록만 해 두고 쓰지 않는다.

# (b) CPU 경량 음량 정규화 + D-1

## b.1 발상

로그가 하는 두 일 중 **음량 불변성만** 싸게 산다. 대역 크기를 로그로 바꾸는
대신, **입력 파형의 레벨을 맞춰** 버린다. FFT 가 필요 없으므로 ① 의 전처리
비용(64×512 FFT)과는 자릿수가 다르다.

## b.2 CLAUDE.md 7장 정책 — **개정 완료 (2026-09-29 승인)**

> 정규화는 학습과 펌웨어에 **비트 단위로 같은 구현**일 때만 허용하고,
> **적용 위치(int8 변환 전/후)를 명시**한다.

원래 금지 근거였던 *"실기기 경로에 정규화가 없다"* 는 펌웨어에도 같이 넣으면
사라진다. 금지해야 할 것은 정규화 자체가 아니라 **한쪽에만 넣는 것**이었다.
데이터 의존 전역 통계와 파일 단위 peak 정규화는 **여전히 금지**다 — 펌웨어가
창 하나만 보고 재현할 수 없다.

동시에 잃는 것이 있다:
- `--floor-zero`(int8 0 비율 하한)와 랜덤 게인 ±12dB 의 근거가 바뀐다.
  정규화가 레벨을 맞추면 게인 증강의 역할이 줄어든다 — **빼지는 말고**
  정규화 상한 위/아래 동작을 덮도록 유지한다.
- dBFS 가 절대 레벨을 뜻한다는 성질을 창 안에서는 잃는다. 데이터 준비 단계
  (창 선택·채움)는 정규화 **이전**이므로 그대로다.

## b.2.5 ★ 두 단계로 나눈다 — int8 위의 정규화는 **정밀도를 되찾지 못한다**

`y = sat8(x · g)` 에서 `x` 가 **이미 int8** 이면, 게인은 **양자화 계단을 함께
키울 뿐**이다. 조용한 소리가 int8 로 깎이면서 잃은 정보는 돌아오지 않는다.

```
원본 float  ──to_int8──▶  int8 (계단 1 LSB = -42.1dBFS)  ──×4──▶  int8 (계단 4 LSB)
                              ↑ 여기서 이미 잃었다            ↑ 계단만 커진다
원본 float  ──×4──▶  float  ──to_int8──▶  int8 (계단 1 LSB, 실효 해상도 +12dB)
                                                ↑ 이쪽이어야 정밀도가 산다
```

펌웨어는 `MicReadChunk()` 가 **int16 을 int8 로 줄이기 전**에 정규화할 수 있다
(CLAUDE.md 7장 "실기기 스케일": `sample >> 14` 뒤 `×4/256` 앞). 즉 **실기기는
좋은 쪽을 할 수 있다.** 그런데 **우리 샤드는 int8 로 저장돼 있다.**

→ 그래서 둘로 나눈다.

| 단계 | 무엇을 | 무엇을 검증하나 | 비용 |
|---|---|---|---|
| **1 (지금)** | 기존 int8 샤드 위에서 **2의 거듭제곱 게인 정규화**. 학습·펌웨어 동일 | **음량 불변성 가설만.** 정밀도 이득은 **없다** | 학습 2회 |
| **2 (효과 있으면)** | 샤드를 int16 으로 재생성하고 **int8 변환 전**에 정규화 | 음량 불변성 + **정밀도** | 재집계 + 학습 |

⚠️ **1단계 결과를 "정규화의 효과" 라고 적으면 안 된다.** 정확히는
**"int8 위에서의 음량 불변성만의 효과"** 이고, 정밀도 몫은 빠져 있다.
1단계가 개선을 보이지 않아도 2단계가 실패라고 말할 수 없다 — 반대로
1단계가 개선을 보이면 그건 **하한**이다.

⚠️ 1단계에서 **2의 거듭제곱 게인을 기본으로 쓰는 이유가 하나 더 생긴다.**
int8 값에 2ⁿ을 곱하는 것은 **정확한 시프트**라 반올림 오차가 없다. 임의 게인
(예 ×2.7)은 int8 위에서 반올림 오차까지 얹어 두 번 깎는다. 1단계에서는
2의 거듭제곱만 돌리고, 임의 게인은 2단계로 미룬다.

## b.3 연산 정의 (학습·펌웨어 공통)

```
peak = max |x[n]|                     n = 0..16383,  x 는 int8 파형
g    = clamp( TARGET / max(peak, 1), 1, GMAX )      # 증폭만, 감쇠 없음
y[n] = sat8( round( x[n] * g ) )
```

| 상수 | 제안값 | 근거 |
|---|---:|---|
| `TARGET` | 96 | 풀스케일 127 대비 −2.4dB. 포화 여유를 둔다 |
| **`GMAX`** | **4 (=+12dB)** | **조용한 창의 잡음을 키우지 않기 위한 상한.** 랜덤 게인 범위와 같은 12dB 로 맞춘다 |
| 감쇠 | **하지 않음** (g ≥ 1) | 큰 소리를 줄이면 이미 포화된 정보가 돌아오지 않는다. 줄여야 할 만큼 크면 그건 클리핑 문제이지 정규화 문제가 아니다 |

**1단계에서는 `g` 를 2의 거듭제곱으로 내림한다** — `g ∈ {1, 2, 4}`.

```
g_pow2 = 2 ** floor(log2(clamp(TARGET / max(peak,1), 1, GMAX)))
y[n]   = sat8( x[n] << log2(g_pow2) )        # 시프트. 반올림 오차 없음
```

int8 위에서 곱하는 것이라 **정확한 시프트가 아니면 반올림으로 한 번 더 깎인다**
(b.2.5). 임의 게인 변형은 int16 샤드가 생기는 **2단계로 미룬다.**
6dB 단위라 ±12dB 변동의 대부분을 흡수한다.

**피크 대신 RMS?** RMS 는 과도음(glass, 0.3초)에서 창 대부분이 조용하므로
게인이 크게 잡혀 **피크가 포화**한다. 피크 기준이 안전하다. RMS 변형은
`GMAX` 를 낮춰 따로 볼 수 있으나 우선순위를 뒤에 둔다.

## b.5 학습 쪽 구현

`datasets/safesound.py` 의 `__getitem__` 에 한 단계 추가. 순서가 중요하다.


정규화가 게인을 그대로 되돌려 증강이 무의미해진다.

⚠️ **테스트셋에도 적용한다** (증강은 아니고 전처리다). 펌웨어가 하는 일이므로
평가 경로에도 있어야 한다. `--config` 에 `wave_fb_norm` 을 추가해 기존
체크포인트 평가와 섞이지 않게 한다.

# (c) NPU 필터뱅크 → CPU 로그 → NPU 분류기

## c.1 발상

(a) 의 치명적 약점은 **로그를 너무 늦게 건다**는 것이다 (a.4). NPU 층 출력이
int8 이라, 대역 크기가 선형으로 깎인 **뒤에** 로그를 씌운다.

(c) 는 그 지점을 **32bit 로 뚫는다.**

```
[NPU 네트워크 1]  파형 (128,128) int8
                    → Conv1d(k=1) + Abs          ← D-1 의 1층 그대로
                    → **wide(32bit) 출력**        ← 여기가 핵심
[CPU]             100×128 int32 → log2 근사 → int8 양자화   (12,800 값)
[NPU 네트워크 2]  (100,128) int8 → voice_conv2 … fc → 로짓 5개
```

CPU 가 하는 일은 **로그 하나뿐**이다. FFT 도 멜 필터뱅크도 없다 — 그것들은
NPU 가 이미 했다. ① 의 CPU 전처리(64×512 FFT + 멜 + 로그)와 비교하면 FFT·멜이
빠진 셈이다.

**이것이 G8 스펙트럼의 ②·③ 사이를 정확히 메운다** (CLAUDE.md 8장 표):
"부분 오프로드" 의 실제 사례이고, 남는 CPU 작업이 **하나의 초월함수**로
최소화된 지점이다.

## c.2 확인할 것 1 — 합성이 되는가

### (i) 두 네트워크 순차 실행

`ai8xize.py` 는 **하나의 yaml = 하나의 네트워크**를 C 프로젝트로 낸다.
두 개를 쓰려면 **각각 합성해 두 `cnn.c`/`weights.h` 를 얻고, 펌웨어가
번갈아 로드**해야 한다. 확인할 항목:

| 항목 | 왜 문제인가 | 확인 방법 |
|---|---|---|
| **가중치 메모리 공유** | 442KB 는 **하나**다. 두 네트워크 가중치가 동시에 올라가야 매 프레임 재로드를 피한다 | 두 yaml 의 `processors` 마스크·커널 오프셋이 겹치지 않게 배치할 수 있는가. `--prefix` 를 달리해 각각 합성한 뒤 `Kernel offset` 합이 442KB 안인지 |
| **재로드 비용** | 겹치면 프레임마다 가중치를 다시 써야 한다. 165KB 를 4Hz 로 쓰는 것은 현실적이지 않다 | 위가 안 되면 (c) 는 기각 |
| **데이터 메모리 재사용** | 네트워크 2 의 입력을 CPU 가 써 넣어야 한다 | `--compact-data` 대신 호스트가 채우는 경로 (`cnn_load_input()` 수정) |
| **상태 전환** | 두 네트워크가 레지스터 설정을 공유하지 않는다 | `cnn_init()` → `cnn_configure()` 를 네트워크마다 부르는 비용 |

우리 모델은 두 조각 합이 지금과 같다 (1층 12,800B + 나머지 152,576B =
165,376B, 37.4%) 이므로 **용량은 문제가 아니다.** 문제는 **배치**다.

### (ii) wide 출력이 네트워크 1 마지막 층에서 되는가

`wide=True`(32bit 출력)를 우리는 지금 **마지막 FC** 에만 쓴다. yaml 에서는
`output_width: 32` 다. 확인할 것:

- `output_width: 32` 가 **Conv1d 층**에서도 받아들여지는가
  (`izer/yamlcfg.py` 의 검증, 지금은 MLP 에만 써 봤다)
- 32bit 출력은 **활성화를 못 붙인다**는 제약이 있는지. 있다면 `Abs` 를
  어떻게 하는가 → **Abs 를 CPU 로 넘긴다** (`abs()` 는 공짜다). 즉
  네트워크 1 = `Conv1d(k=1)` 만, CPU 가 `|·|` 와 로그를 함께 한다
- 데이터 메모리: 32bit 출력은 채널당 픽셀을 **4배** 먹는다.
  100채널 × 128 × 4B = 51,200B, 채널당 128 px × 4 = **512 px** (한계 8,192 의
  6.3%). 여유롭다

> ⚠️ 이 둘은 **문서가 아니라 합성으로** 확인한다. `synthesis/` 에
> `safesound-fb-stage1.yaml`(1층 + wide) 과 `safesound-fb-stage2.yaml` 을
> 만들어 `ai8xize.py` 를 돌리는 것이 유일한 답이다.

## c.3 확인할 것 2 — CPU 비용

### 로그 근사 — 12,800 값 (100채널 × 128프레임)

int32 → 로그 → int8 을 값마다 한 번. 후보 셋.

| 방식 | 값당 사이클 (추정) | 12,800 값 | 정확도 |
|---|---:|---:|---|
| `logf()` (libm, float) | ~100+ | ~1,280,000 | 완전 |
| **CLZ 기반 log2 + 선형 보간** | **~8** | **~102,000** | 약 0.05 bit |
| **CLZ 기반 log2 + 16엔트리 LUT** | **~6** | **~77,000** | 약 0.02 bit |
| 상위 8bit LUT (256엔트리) 만 | ~4 | ~51,000 | 지수부만, 조악 |

**CLZ 방식이 표준이다.** Cortex-M4 의 `CLZ` 명령이 1사이클이다.

```c
// v > 0 인 int32 -> Q8.8 형식의 log2(v) 근사
static inline int32_t log2_q8(uint32_t v) {
    int32_t e = 31 - __CLZ(v);              // 지수부 (1 cyc)
    uint32_t m = (e >= 8) ? (v >> (e - 8)) : (v << (8 - e));  // 상위 9bit 정규화
    return (e << 8) + LUT[m & 0xFF];        // 가수부는 256엔트리 LUT
}
```

- `LUT[256]` 은 512B (int16). Flash 512KB 중 무시할 양
- 값당: CLZ 1 + 시프트 2 + 로드 2 + 덧셈 1 ≈ **6사이클**
- 이후 int8 양자화: 곱·시프트·`__SSAT` ≈ 3사이클
- **합계 약 9사이클 × 12,800 = 약 115,000 사이클 = 1.15ms @100MHz**

⚠️ **전부 추정이다** (CLAUDE.md 10장). 보드에서 DWT 로 잰다.

### NPU ↔ CPU 데이터 이동

| 방향 | 양 | 비용 |
|---|---:|---|
| NPU 데이터메모리 → CPU 읽기 | 100×128×4B = **51,200 B** | 32bit 워드 12,800회 로드 |
| CPU → NPU 데이터메모리 쓰기 | 100×128×1B = **12,800 B** | 워드 단위 3,200회 저장 |

CNN 데이터 메모리는 M4 에서 메모리 맵으로 보인다(`cnn_unload()` 가 이미 그렇게
한다). 스트리밍 없이 단순 루프면 **워드당 약 2사이클** → 읽기 ~26,000 +
쓰기 ~6,400 ≈ **32,000 사이클 = 0.32ms**.

⚠️ 실제로는 **로그 루프에 융합**한다 (읽고 → 로그 → 바로 쓴다). 그러면 이동
비용이 로그 루프에 흡수되어 별도로 들지 않는다. 위 표는 상한이다.

### 총 CPU 비용 추정

| 항목 | 사이클 | ms @100MHz |
|---|---:|---:|
| 로그 + 양자화 (융합) | ~115,000 | 1.15 |
| 데이터 이동 (융합 시 흡수) | 0~32,000 | 0~0.32 |
| **합** | **~115,000~147,000** | **1.15~1.47** |
| 참고: NPU 추론 전체 (현행) | 71,718 | 0.72 |
| 참고: (a) NPU 로그 근사 | ~160,000 | ~1.6 (전부 NPU) |

→ **(c) 의 CPU 비용은 (a) 의 NPU 증분과 비슷한 자릿수다.** 차이는 *어디서*
쓰느냐다. NPU 가 M4 보다 에너지 효율이 높다면 (a) 가 유리하고, (c) 는 대신
**정확도 손실이 없을 가능성**을 산다. **이 맞교환이 G8 의 핵심 그림이 된다.**

## c.4 확인할 것 3 — 학습 경로를 비트 단위로 맞추기

가장 까다로운 부분이다. 학습에서도 **같은 위치에 같은 연산**이 들어가야 한다.

```
학습:  x(int8) → conv1(float) → |·| → [양자화 흉내] → log2_q8 근사 → int8 → conv2…
펌웨어: x(int8) → conv1(NPU,int32) → |·|(CPU) → log2_q8(CPU) → int8 → conv2(NPU)
```

맞춰야 할 것 넷.

1. **conv1 출력의 스케일.** NPU 는 int8 가중치 × int8 입력을 int32 로 누적하고
   `output_shift` 를 적용한다. 학습(float)에서 같은 정수 스케일을 재현하려면
   **QAT 상태의 conv1 출력을 정수로 읽어야** 한다. `ai8x` 의 QAT 모듈이
   `output_shift` 를 들고 있으므로, 커스텀 `nn.Module` 에서 그 값을 써서
   `round(x * 2**shift)` 로 정수화한다.
2. **로그 근사를 학습에서도 같은 함수로.** `log2_q8` 의 파이썬 판을
   `datasets/` 가 아니라 **모델 안**에 둔다 (파형이 아니라 활성화에 걸리므로).
   LUT 는 같은 512B 테이블을 공유한다.
3. **역전파.** `log2_q8` 는 계단 함수라 미분이 0 이다 → **STE**(straight-through
   estimator)로 `d/dx log2(x) = 1/(x ln2)` 를 흘린다. `ai8x` 의 양자화 모듈이
   이미 STE 를 쓰므로 같은 패턴을 따른다.
4. **KAT.** `tools/kat_logstage.py` — 같은 입력에 대해 (파이썬 log2_q8) 와
   (C log2_q8 을 x86 으로 빌드한 것) 의 출력이 **비트 단위로 같은지** 전수

# (a)(b)(c) 정리 — **CPU 에 남는 전처리의 양** 축

G8 의 스펙트럼(CLAUDE.md 8장)을 우리 실측 위에 다시 그린 것이다.

| | CPU 가 하는 일 | NPU 가 하는 일 | **CPU 비용 (전부 추정)** | **NPU 비용 (추정)** | 정확도 | 상태 |
|---|---|---|---:|---:|---|---|
| **①** | **STFT + 멜 + 로그** (64×512 FFT) | 2D CNN | 수십만 사이클 (TBD) | 기준 | **0.6732** (3시드) | 실측 완료 |
| **(c)** | **로그만** (12,800값 CLZ+LUT) | 대역분해 + 분류기 | **~115k (1.15ms)** | 기준 | ? — S2 sim 으로 먼저 본다 | **설계** |
| **(b)** | **음량 정규화만** (16,384샘플 시프트) | 대역분해 + 분류기 | **~41k (0.41ms)** | 기준 | ? | **설계, 1단계 먼저** |
| **(a)** | **없음** | 대역분해 + **로그 근사** + 분류기 | 0 | **2.23배** | ? — S1 sim 이 부정적이면 기각 | 설계 |
| **D-1** | 없음 | 대역분해 + 분류기 | 0 | 기준 | 0.4944 (3시드) | 실측 완료 |
| **④** | 없음 | 분류기만 | 0 | 기준 | 0.3590 (2시드) | 실측 완료 |

**축의 뜻**: 위로 갈수록 CPU 가 많이 하고(①), 아래로 갈수록 NPU 가 다 한다(④).
(c)→(b)→(a) 가 그 사이를 **CPU 작업량 순으로** 메운다.

**논문에서 이 표가 하는 일**

1. G8 의 "전처리 오프로드 스펙트럼" 이 ①②③④ 네 점이 아니라 **연속 축**임을
   보인다. 그리고 각 점이 *무엇을* 남기는지가 구체적 연산으로 적힌다.
2. **"마지막 한 연산" 의 비용**을 드러낸다 — **가설**: (c) 는 CPU 에 로그
   하나만 남겼는데도 약 1.15ms 로 NPU 추론 전체(0.72ms)보다 비쌀 수 있다.
   사실이라면 "가속기 친화적이지 않은 연산은 **하나만 남아도 파이프라인을
   지배한다**" 가 된다.
   ⚠️ **아직 가설이다.** CPU 쪽 1.15ms 는 명령 수 기반 추정이고, NPU 쪽
   0.72ms 는 합성 로그의 사이클 수(71,718)를 100MHz 로 나눈 값이다 — 둘은
   측정 방식이 달라 직접 비교가 이미 불공정하다. **보드에서 DWT 로 같은
   방식으로 재기 전에는 이 문장을 논문에 쓰지 않는다** (CLAUDE.md 10장).
3. (a) vs (c) 가 **같은 일을 어디서 하느냐**의 대조다. (a) 는 NPU 2.23배,
   (c) 는 CPU 1.15ms. 에너지 축에서 어느 쪽이 싼지는 **보드 실측**이 답한다 —
   그 측정이 G3·G8 을 잇는다.

⚠️ **표의 CPU·NPU 비용 열은 전부 추정치다.** 근거가 서로 다르다 —
(a) 는 MAC 비례 외삽, (b)·(c) 는 명령 수 손계산, ① 은 아예 미상(TBD).
**서로 비교할 수 있는 값이 아니다.** 확정은 합성 로그(`Total ... cycles`)와
보드 DWT 실측이며, 그전까지 표는 **순서를 잡는 용도**로만 쓴다.
정확도 열의 물음표는 학습 전이라는 뜻이다.

# 우선순위 제안

| | (a) NPU 로그 근사 | (b) CPU 음량 정규화 | (c) 중간에 CPU 로그 |
|---|---|---|---|
| 선행 확인 | `sim_late_log.py` S1 | 없음 | 합성 2건 + `sim` S2 + KAT |
| 학습 | 1~2회 | 1단계 1~2회 | 1~2회 (모델 재정의 필요) |
| CPU 비용 | 0 | ~41k (0.41ms) | **~115k (1.15ms)** |
| NPU 비용 | **2.23배** | 그대로 | 그대로 (두 번 호출) |
| 정책 변경 | 없음 | 7장 개정 **완료** | 없음 |

**순서: (b) → sim(S1·S2) → (c) 또는 (a).**

1. **(b) 1단계** 를 먼저 한다. 선행 확인이 필요 없고, 싸고(25분 × 1~2회),
   실패해도 "음량 불변성만으로는 부족하다" 는 정보가 남는다.
2. 그와 **병행해 `tools/sim_late_log.py`** 를 돌린다 (학습 없음, 비용 0).
   S1(=(a) 경로) 과 S2(=(c) 경로) 를 비교해 **(a) 와 (c) 중 어느 쪽을 할지**
   정한다. S2 ≫ S1 이면 (c), 둘 다 S0 에 가까우면 싼 (a) 를 먼저.
3. 그다음 합성 확인 → 학습.

라운드 6 결과(`g8-round6-logcompression.md`)가 **로그의 음량 불변성**을
주원인으로 지목했으므로, (b) 가 그 성질을 가장 직접적으로 겨냥한 안이다.

# 구성별 비용 비교 — ⚠️ **에너지는 보드 실측 전이라 미정**

| 구성 | CPU 전처리 | NPU 사이클 | 가중치 | @300/h | **추론당 에너지** |
|---|---|---:|---:|---:|---|
| **①** | **STFT 64×512 + 멜 + 로그** | 157K params 2D CNN (합성 미실시) | — | **0.6708** | **미정** |
| **(a)** | 없음 | **274,726** (D-1 의 3.83배) | 55.5% | 0.5572 | **미정** |
| (c) | CLZ+LUT log2 12,800값 (~115k 사이클 추정) | 71,718 ×2회 호출 | 37.4% | 미실행 | **미정** |
| **D-1** | 없음 | **71,718** | 37.4% | 0.5072 | **미정** |
| ④ | 없음 | 71,718 | 37.4% | 0.5145 | **미정** |

**읽는 법**
- **(a) 는 정확도 +0.050 을 연산 3.83배로 샀다.** 에너지 축에서 남는
  장사인지는 **보드 실측이 답한다**.
- **① 은 그보다 +0.114 가 더 높지만 CPU 에 FFT 가 남는다.** ①의 NPU 쪽은
  아직 합성하지 않았다 — 2D CNN 이라 사이클 수가 다르다.
- **(c) 를 버리지 않는 이유**: (a) 와 같은 이득을 **CPU 1.15ms** 로 살 수
  있다면 NPU 3.83배보다 쌀 수 있다. 어느 쪽이 싼지는 **에너지 실측 전에는
  말할 수 없다.**

⚠️ **에너지 칸을 추정으로 채우지 않는다** (CLAUDE.md 10장). 사이클 수는
합성 로그의 값이고, CPU 쪽은 명령 수 손계산이라 **서로 비교할 수 없다**.
`scripts/analyze_power.py` 가 준비돼 있고, 보드 + 외부 계측 장비가 있어야
채워진다.

> 참고 출처: 선행연구가 보고한 MFCC 전처리 에너지 **826 µJ** 는 **다른
> 하드웨어·다른 구성**의 값이다. 우리 수치가 아니며 표의 칸을 채우는 데
> 쓰지 않는다. 자릿수 감각을 위한 인용으로만 둔다.
