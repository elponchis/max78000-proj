# 구성 ① 설계안 — 로그 멜 + 2D CNN (G8 대조군)

작성 2026-09-26. **설계안이며 구현 전이다.** 확정 전에 승인받는다.

G8(전처리 오프로드 스펙트럼)의 최소 버전은 ①과 ④ 두 점 비교로 성립한다
(`CLAUDE.md` 8장). ④(raw 파형 1D CNN)는 이미 기준선이고, 여기서 정의하는 것은
**①: 전처리를 M4 CPU 가 전부 하고 NPU 는 2D CNN 만 하는 구성**이다.

핵심 원칙: **입력 표현만 다르게 하고 나머지는 전부 같게 한다.** 클래스 손실
가중치, 증강, 에폭 수, 스케줄, QAT 정책, 평가 스크립트, 원본 단위 분할이 모두
동일해야 "전처리 위치가 정확도·지연에 미치는 영향" 이라는 결론이 성립한다.

## 1. 특징 표현

| 항목 | 값 | 근거 |
|---|---|---|
| STFT | n_fft 512 (32ms), hop 256 (16ms), Hann, `center=False` | 256 은 2의 거듭제곱이라 M4 FFT 에 유리. center 패딩은 실기기에서 미래 샘플을 요구하므로 쓰지 않는다 |
| 프레임 수 | **64** | (64−1)×256+512 = 16,640 샘플 = 1.04초. 샤드 1.2초 안에 들어간다 |
| 멜 | n_mels **64**, fmin 20Hz, fmax 8000Hz | 64×64 정사각 입력 |
| 압축 | `10·log10(mel_power + eps)` | dB. **DCT 는 걸지 않는다** (아래 1.1) |
| 양자화 | 고정 스케일 dB 구간 → int8, 창·파일 단위 정규화 없음 | `CLAUDE.md` 7장 스케일 정책을 그대로 따른다 |
| 입력 텐서 | **1 × 64 × 64 int8** | 4,096 바이트 |

### 1.1 MFCC 가 아니라 로그 멜을 쓰는 이유

G8 의 ① 은 표에서 "MFCC 전체" 로 적혀 있으나, 실제 입력은 **로그 멜에서 끊는다.**
이유는 셋이다.

1. **DCT 는 CNN 에 손해다.** 켑스트럼 역상관은 GMM-HMM 시대의 요구이고, 2D CNN 은
   멜 축의 국소 상관을 오히려 특징으로 쓴다. DCT 를 걸면 ① 의 정확도가 내려가고,
   그러면 "①이 ④보다 정확하다" 는 대조가 우리에게 유리하게 왜곡된다.
   **대조군에는 최선의 구성을 준다.**
2. **비용 논거가 흔들리지 않는다.** ① 의 CPU 비용을 지배하는 것은 FFT 이고 DCT 는
   그 일부다. 그래서 지연 비교의 결론은 바뀌지 않는다.
3. DCT 까지의 CPU 비용은 **펌웨어에서 따로 잰다** (DCT on/off 두 측정).
   논문에는 "로그 멜까지 / MFCC 까지" 두 값을 병기한다.

→ 논문 서술은 "① 전처리 = STFT + 멜 필터뱅크 + 로그 (선택적 DCT)" 로 수정한다.
`CLAUDE.md` 8장 G8 표도 함께 고친다.

### 1.2 dB → int8 변환 상수는 **실측 후 확정한다**

`lm8 = clip(round((lm_db − TOP_DB) × 255/SPAN_DB + 127), −128, 127)` 형태를 쓰되
`TOP_DB`, `SPAN_DB` 는 v1 데이터셋에서 클래스별 분포를 재고 정한다
(`tools/mel_range_sweep.py` 신설, `zero_ratio_by_class.py` 와 같은 방식).
지금 숫자를 적지 않는 이유는 10장 규칙이다 — 측정 전이면 TBD.

기준은 파형 쪽과 같다. **창 단위·파일 단위 정규화를 하지 않는다.** 실기기가
정규화를 못 하기 때문이다(7장). 따라서 조용한 창은 멜 축에서도 바닥에 붙는다.

## 2. 증강을 어떻게 같게 유지하는가 ← 설계의 쟁점

파형 모델의 증강은 둘이다. 둘 다 **파형 영역**에 정의돼 있다.

| 증강 | 파형 모델 | 멜 모델에서 |
|---|---|---|
| 시간축 shift ±100ms | 1.2초 샤드에서 **샘플 단위** 재절단 | **프레임 단위(16ms) 재절단** ← 해상도 차이 |
| 랜덤 게인 ±12dB | 곱셈 후 피크 클램프, int8 0 비율 초과 시 재추출 | 동일 (파형에서 먼저 적용) |

### 왜 "특징 미리 계산" 을 그대로 할 수 없나

게인은 로그 영역에서 **상수 덧셈과 동등해 보이지만 실제로는 아니다.** 피크 클램프와
int8 포화가 비선형이기 때문이다. 미리 계산한 멜에 상수를 더하면, 클리핑이 일어나는
큰 소리에서 학습 분포가 파형 경로와 갈라진다 — 그러면 "입력 표현만 다른 비교" 가
깨진다.

### 채택안: 데이터로더에서 즉석 계산, 테스트셋만 캐시

- `datasets/safesound_mel.py` 가 **기존 int8 샤드를 그대로 읽는다.** 새 전처리
  산출물을 만들지 않는다 (같은 창, 같은 분할, 같은 필터 — 완전 동일성 보장).
- `__getitem__`: 샤드 1.2초 int8 → (shift 재절단 → 게인 → 피크 클램프 → int8) →
  STFT → 멜 → dB → int8. **앞 절반은 `safesound.py` 의 함수를 그대로 호출**한다.
- 비용: 창당 약 1ms. 13.5k 창 / `--workers 4` → 에폭당 3~4초. 무시할 수준이고
  GPU 학습과 겹쳐 사라진다.
- 테스트셋은 증강이 없으므로 **첫 평가 때 memmap 으로 캐시**한다 (`--mel-cache`).
  이후 평가·스윕·스트리밍은 캐시를 읽어 파형 경로와 같은 속도로 돈다.

→ 사용자의 "PC 에서 미리 계산" 의도는 지켜진다. **MCU 는 학습에 전혀 관여하지
않고**, 반복 평가 경로는 실제로 미리 계산된다. 다만 학습 경로만은 증강 동일성을
위해 즉석 계산이 필요하다. 이 점이 설계 판단이라 여기 명시한다.

⚠️ shift 해상도 차이(1샘플 vs 16ms)는 **없앨 수 없다** — 프레임 격자가 16ms 이기
때문이다. 논문에 한계로 적는다. 영향을 줄이려면 멜 모델의 shift 를 16ms 배수로
제한하고 파형 모델도 같은 격자로 맞추는 대조 실험을 하나 더 돌릴 수 있다
(선택 사항, 학습 1회 추가).

## 3. 모델 — MAX78000 제약 안의 2D CNN

지원 연산은 Conv2d **3×3 / 1×1 만**, MaxPool/AvgPool, element-wise 다
(`CLAUDE.md` 3장). depthwise separable 은 MAX78000 에서 **미지원**이라 쓸 수 없다.

파라미터 수를 1D 기준선(165,457 / 36.6%)에 최대한 붙여 **용량 차이가 결론을
오염시키지 않게** 한다.

| # | 연산 | 출력 | params |
|---|---|---|---:|
| in | — | 1×64×64 | — |
| 1 | Conv2d 3×3, 1→32 + MaxPool2 | 32×32×32 | 320 |
| 2 | Conv2d 3×3, 32→32 + MaxPool2 | 32×16×16 | 9,248 |
| 3 | Conv2d 3×3, 32→64 + MaxPool2 | 64×8×8 | 18,496 |
| 4 | Conv2d 3×3, 64→64 + MaxPool2 | 64×4×4 | 36,928 |
| 5 | Conv2d 3×3, 64→128 | 128×4×4 | 73,856 |
| 6 | Conv2d 1×1, 128→128 + MaxPool2 | 128×2×2 | 16,512 |
| 7 | FC 512→5 | 5 | 2,565 |
| | | **합계** | **157,925** |

**442KB 대비 35.7%** (1D 기준선 36.6%). 8bit 기준이고, 모델 규모 스윕(도전 1순위)
에서 ×1.5 까지 올려도 8bit 상한 안이다.

데이터 메모리: 최대 중간 텐서는 1층 출력 32×64×64 = 131KB (512KB 의 26%).
채널당 4,096 바이트로 프로세서당 8KB 한도 안이다. **확정은 `ai8xize.py` 합성
결과로 한다** (3장 규칙).

부수 사항
- BatchNorm 은 전 층에 넣고 학습 후 fold (ai8x `FusedConv2dBNReLU` 사용).
- 마지막 FC 전에 `ai8x.FusedAvgPoolConv2d` 대신 MaxPool 을 쓴 것은 1D 기준선과
  풀링 종류를 맞추기 위함이다. 기준선이 AvgPool 이면 여기도 AvgPool 로 바꾼다
  (구현 시 `models/ai85net-safesound.py` 확인).
- Softmax 는 CPU (3장).

## 4. 같게 맞출 것 / 다를 수밖에 없는 것

**같게** — 이게 지켜지지 않으면 비교가 무의미하다.

- 데이터: **같은 v1 샤드**, 같은 원본 단위 분할, 같은 필터·채움·오버라이드
- 클래스 손실 가중치: `safesound.class_weights()` 를 그대로 재사용
  (`V1_TRAIN_COUNTS` 공유)
- 증강 범위: shift ±100ms(siren ±200ms), 게인 ±12dB 전 클래스 동일, MSnoise 미적용
- 에폭 150, 같은 `schedule_safesound.yaml` / `qat_policy_safesound.yaml`
- 평가: `eval_confusion.py` / `eval_threshold.py` / `stream_eval.py` 를 그대로.
  창 단위 + 원본 단위 혼동행렬, 원본 부트스트랩 CI, 시간당 오경보
- 랜덤 시드

**다를 수밖에 없는 것** — 논문에 명시한다.

1. 모델 구조 (1D vs 2D). 파라미터 수를 맞춰 완화하되 동일하지는 않다
2. shift 해상도 (1샘플 vs 16ms)
3. 학습 시간 (멜 계산분 추가)
4. 실기기 전처리 오차: M4 고정소수점 FFT 결과가 PC float 과 다르다 → **G4(온디바이스
   vs PC 괴리)가 ① 에서 ④ 보다 크게 나올 것으로 예상**된다. 이것 자체가 결과다

## 5. 구현 순서 (승인 후)

1. `tools/mel_range_sweep.py` — v1 에서 로그 멜 dB 분포를 클래스별로 재고
   `TOP_DB`/`SPAN_DB` 를 정한다. 표를 `docs/results/` 에 남긴다
2. `datasets/safesound_mel.py` — 위 2절 구조. `datasets` 딕셔너리에
   `SafeSoundMel` 등록, `weight` 는 파형과 동일
3. `tools/kat_safesound_mel.py` — 멜 경로 KAT. 저장 벡터로 **펌웨어의 M4 FFT
   결과와 비트 단위 비교**할 기준을 미리 만든다 (보드 도착 후 재사용)
4. `models/ai85net-safesound-mel.py` — 3절 구조
5. `ai8xize.py` 합성으로 442KB / 512KB 조기 검증 (학습 전에)
6. Colab 셀 추가 — 같은 스케줄로 150에폭, 같은 평가
7. `docs/results/` 에 ① vs ④ 표: macro-F1(원본 단위) · 클래스별 재현율 · CI ·
   시간당 오경보. **지연·에너지는 보드 확보 후**다 (13장)

⚠️ 지금 시점의 우선순위 문제: **④ 기준선이 과소적합(train Top1 61~64%)이다.**
④ 가 자기 데이터도 못 맞히는 상태에서 ① 을 학습하면 두 점 모두 의미가 없다.
① 학습은 ④ 의 과소적합을 푼 뒤에 돌리는 것이 맞다 — 다만 1~5번(설계·검증 코드·
합성 검증)은 ④ 와 무관하므로 먼저 해도 낭비가 아니다.
