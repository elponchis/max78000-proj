# (c) 설계안 — NPU 필터뱅크 → CPU 정수 로그 → NPU 분류기

**추정만 한다. 실행은 승인 후.** (2026-10-01)

```
[NPU-1] 파형 (128,128) int8 → Conv1d(k=1, 128탭 멜 FIR) → **wide(32bit) 출력**
[CPU ]  100×128 int32 → |·| → CLZ+LUT 정수 log2 → int8 양자화
[NPU-2] (100,128) int8 → voice_conv2 … fc → 로짓 5개
```

---

## 1. 왜 지금 (c) 인가 — 가설과 근거

**가설**: ①−④ 격차의 주원인은 **로그의 위치**가 아니라 **로그 이전의
정밀도**다.

`tools/sim_late_log.py` (① 모델 기준 시뮬레이션, 회복률):

| 경로 | 무엇이 다른가 | 회복률 |
|---|---|---:|
| **S2 = (c)** | log **이전**이 int32 | **99.7%** |
| S1 = (a) 정확한 로그 | log 이전이 **int8** | 93.3% |
| S1b = (a) 구간선형 K=4 | 〃 + 근사 오차 | 88.7% |
| **(a) 실측 (5시드)** | 〃 + 재학습 | **79.9%** (① 대비) |

- **정밀도 몫** (S1b → S2, int8 → int32): **+11.0%p**
- **근사 몫** (S1 → S1b, 정확한 로그 → 구간선형 K=4): **−4.6%p**
- → **정밀도 몫이 근사 몫의 2.4배.**

(a) 가 5시드에서 ④를 넘지 못한 것(+0.003, CI [−0.028, +0.034])이 이 가설과
정합적이다. 로그를 **NPU 안에 넣는 것 자체**는 D-1 대비 +0.0285 로 효과가
있었지만(CI [+0.0035, +0.0534]), **int8 로 깎인 뒤에 걸어서** 상한이 낮았다.

⚠️ sim 은 **① 모델로 평가한 상한**이다. (a) 실측 79.9% 가 S1b 예측 88.7%
보다 **8.8%p 낮은 것이 재학습 효과의 크기**다. (c) 도 같은 정도로 깎인다면
99.7% → 실측 **약 91%** (≈ 0.61) 를 기대하게 되는데, 이건 **외삽이다.**

## 2. 합성 가능 여부 — 확인할 것 넷

### 2.1 ★ 두 네트워크가 442KB 에 **동시에** 올라가는가

가장 큰 위험이다. 가중치 메모리는 **하나**다.

| 조각 | 층 | 가중치 |
|---|---|---:|
| NPU-1 | voice_conv1 (128→100, k=1) | **12,800 B** |
| NPU-2 | voice_conv2 … fc (8층) | **152,576 B** |
| 합 | | **165,376 B (37.4%)** |

용량은 문제가 아니다 — **지금 D-1 과 같다.** 문제는 **배치**다:
두 yaml 의 `Kernel offset` 이 겹치지 않아야 프레임마다 가중치를 다시 쓰지
않는다. 165KB 를 4Hz 로 재기록하는 것은 현실적이지 않다.

확인: `--prefix` 를 달리해 각각 합성한 뒤 두 로그의 `Kernel offset` /
`Kernel length` 가 겹치는지 본다. 겹치면 `processors` 마스크로 분리한다.

### 2.2 `output_width: 32` 가 **Conv1d 층**에서 되는가

지금은 마지막 MLP 에만 썼다 (`wide=True`).

- 안 되면 → **Abs 를 CPU 로 넘긴다.** NPU-1 = `Conv1d(k=1)` 만, CPU 가
  `|·|` 와 로그를 함께 한다. `abs()` 는 공짜라 비용이 늘지 않는다.
- 32bit 출력은 활성화를 못 붙일 가능성이 크므로 **애초에 이 구성이 자연스럽다.**

데이터 메모리: 100채널 × 128 × 4B = **51,200 B**, 채널당 **512 px**
(HWC 한계 8,192 의 6.3%). 여유롭다.

### 2.3 NPU-2 의 입력을 CPU 가 써 넣을 수 있는가

`--compact-data` 는 샘플 데이터를 C 배열로 박는다. 실제로는 **호스트가
데이터 메모리에 직접 쓴다** (`cnn_load_input()` 수정). `cnn_unload()` 가
이미 메모리 맵 접근을 하므로 반대 방향도 된다.

### 2.4 네트워크 전환 비용

`cnn_init()` → `cnn_configure()` 를 프레임마다 두 번 부른다. 레지스터
설정만이라 **수백 사이클 수준**으로 보이나 **측정 전에는 모른다**.

## 3. 학습에서 bit-identical 재현

가장 까다로운 부분이다. **CPU 정수 로그가 학습과 펌웨어에서 비트 단위로
같아야** 한다 (CLAUDE.md 7장 정규화 원칙과 같은 요구).

### 3.1 맞춰야 할 것 넷

| # | 항목 | 방법 |
|---|---|---|
| 1 | **conv1 출력의 정수 스케일** | NPU 는 int8 가중치 × int8 입력을 int32 로 누적하고 `output_shift` 를 적용한다. 학습(float)에서 같은 정수를 재현하려면 QAT 모듈의 `output_shift` 를 읽어 `round(x · 2^shift)` 로 정수화한다 |
| 2 | **로그 근사 함수** | `log2_q8()` 의 **파이썬 판과 C 판이 같은 LUT·같은 시프트**를 쓴다. LUT 256엔트리(int16, 512B)를 **하나의 소스**에서 생성해 양쪽이 공유 |
| 3 | **역전파** | 계단 함수라 미분이 0 → **STE**. `d/dx log2(x) = 1/(x ln2)` 를 흘린다. `ai8x` 의 양자화 모듈이 이미 STE 를 쓰므로 같은 패턴 |
| 4 | **int8 재양자화** | 로그 출력 → int8 은 고정 아핀. `melfeat.db_to_int8` 과 같은 규약(포화, 랩어라운드 금지) |

### 3.2 KAT — **이게 통과하지 않으면 (c) 를 하지 않는다**

`tools/kat_logstage.py`:
- int32 입력 범위를 **로그 스케일로 훑어** 파이썬 `log2_q8` 과
  **x86 으로 빌드한 C `log2_q8`** 의 출력을 전수 비교
- 표본 1e8 개 정도 (경계값 집중: 0, 1, 2^k−1, 2^k, 2^k+1, INT32_MAX)
- **한 비트라도 다르면 실패.** train/serve 불일치는 G4 를 통째로 오염시킨다

### 3.3 모델 정의

`models/ai85net-safesound-cstage.py` (신규). 기존 파일을 건드리지 않는다.

```python
class AI85SafeSoundCStage(nn.Module):
    # NPU-1: Conv1d(128→100, k=1), 활성화 없음 (wide 출력)
    # [CPU]  IntLog2(STE)  ← 학습에서는 여기가 커스텀 autograd.Function
    # NPU-2: voice_conv2 … fc  (D-1 과 동일)
```

⚠️ **학습은 한 덩어리로 한다.** 두 네트워크로 쪼개는 것은 **합성·펌웨어
단계**의 일이고, 학습에서는 중간에 CPU 연산이 낀 하나의 모델이다.

## 4. 비용 추정 — **전부 추정이다**

### 4.1 CPU 로그 비용

12,800 값 (100채널 × 128프레임), Cortex-M4 100MHz.

```c
static inline int32_t log2_q8(uint32_t v) {
    int32_t e = 31 - __CLZ(v);                              // 1 cyc
    uint32_t m = (e >= 8) ? (v >> (e - 8)) : (v << (8 - e)); // 2 cyc
    return (e << 8) + LUT[m & 0xFF];                        // 2~3 cyc
}
```

| 항목 | 값당 | 12,800 값 |
|---|---:|---:|
| `|·|` + log2_q8 | ~7 cyc | ~89,600 |
| int8 양자화 (곱·시프트·`__SSAT`) | ~3 cyc | ~38,400 |
| **합 (융합)** | **~10 cyc** | **~128,000 (1.28 ms)** |

데이터 이동(NPU 메모리 읽기 51,200 B + 쓰기 12,800 B)은 **로그 루프에
융합**하면 별도로 들지 않는다.

### 4.2 구성별 비교 — 에너지는 **미정**

| 구성 | CPU | NPU 사이클 | 가중치 | @300/h | 에너지 |
|---|---|---:|---:|---:|---|
| ① | STFT 64×512 + 멜 + 로그 | (2D, 미합성) | — | **0.6708** | 미정 |
| **(c)** | **로그만 ~128k (1.28ms)** | 71,718 (2회 호출) | 37.4% | **추정 ≈0.61** | 미정 |
| (a) | 없음 | **274,726 (3.83배)** | 55.5% | 0.5357 | 미정 |
| ④ | 없음 | 71,718 | 37.4% | 0.5329 | 미정 |

⚠️ **(c) 의 0.61 은 외삽이다** (sim 99.7% × (a) 의 재학습 감쇠 비율).
근거가 약하므로 **논문에 쓰지 않고**, 착수 여부 판단에만 쓴다.

⚠️ CPU 사이클(명령 수 손계산)과 NPU 사이클(합성 로그)은 **서로 비교할 수
없다**. 에너지 축의 답은 보드 실측이다.

### 4.3 학습 비용

| 항목 | 값 |
|---|---:|
| 모델 규모 | D-1 과 같다 (165K params) + CPU 로그 층 |
| 학습 1회 | **약 30~40분** (WSL CPU) — D-1 25분 + 로그층 오버헤드 |
| **5시드** | **약 2.5~3.5시간** |
| 선행 KAT | 약 1시간 (구현 + 검증) |
| 합성 확인 | 약 1시간 |
| **합계** | **약 5~6시간** |

⚠️ 로그층은 `torch` 정수 연산이라 vectorize 가 잘 되면 오버헤드가 작지만,
**STE 커스텀 함수라 느려질 수 있다.** 첫 3에폭으로 재고 150에폭 예상이
1시간을 넘으면 멈춘다 (chain6 과 같은 게이트).

## 6. 이 실험의 값어치

**결과가 어느 쪽이든 논문에 쓴다.**

| 결과 | 논문에서의 뜻 |
|---|---|
| (c) ≫ ④ | **"로그는 옮길 수 있다 — 단 정밀도를 지킨 채로."** G8 스펙트럼의 ②·③ 사이가 실제로 유효한 지점임을 보인다 |
| (c) ≈ ④ | **"로그 위치·정밀도로는 안 된다."** 격차의 원인이 더 앞단(표현 자체)에 있다는 뜻 — ①의 2D 구조·멜 스케일로 후보가 좁혀진다 |

그리고 어느 쪽이든 **"CPU 에 로그 하나만 남겨도 1.28ms"** 라는 수치가 남는다.
NPU 추론 전체가 0.72ms 이므로, **가속기 친화적이지 않은 연산은 하나만
남아도 파이프라인을 지배한다**는 주장의 근거가 된다.
⚠️ 두 값은 측정 방식이 달라 직접 비교가 불공정하다 — **보드 DWT 로 같은
방식으로 재기 전에는 논문에 쓰지 않는다.**
